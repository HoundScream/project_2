# Парсеры: функционал и границы

Документ описывает, что делает каждый модуль парсинга, какие данные он принимает
и отдаёт, как обрабатывает ошибки и как его расширять. Код пишется после
согласования этого описания.

Общая идея: сетевой слой приносит **сырой HTML**, парсер превращает его в
`LiveMapCardData`. Больше ни одна стадия не ходит в сеть и не знает, откуда
пришёл HTML. Это позволяет менять любой парсер и чинить его, не трогая
остальные части.

---

## geonetix-core

Типы данных и простые примитивы, которыми пользуются все остальные крейты.

**Умеет:**
- хранить 35 общих типов предметной области (`LiveMapCardData`, `MapPlatform`,
  `QueryAnalysis`, отчёты, сценарии подписки и т.д.);
- `text::collapse_whitespace` — схлопывать пробелы и переносы строк в тексте.

**Не умеет:** ходить в сеть, знать про базу, знать про HTTP-клиент.

**Расширение:** новый тип поля добавляется сюда и сразу становится доступен
всем крейтам.

## geonetix-parse-jsonld — готов

Читает schema.org-разметку из HTML.

**Вход:** HTML-документ (`scraper::Html`).
**Выход:** `Option<String>` / `Option<f32>` по заданному пути.

**Правила:**
1. Берутся только `<script type="application/ld+json">`.
2. Скрипт, который не распарсился, пропускается молча — остальные читаются дальше.
3. Путь ищется по ключам объектов; если встречается массив, поиск идёт по всем
   элементам.
4. Число принимается и как число, и как строка; запятая заменяется на точку
   (`"4,7"` → `4.7`).
5. Текст схлопывается, пустой результат считается отсутствием значения.
6. Берётся первый подходящий скрипт.

**Тесты:** 17 фикстур на HTML. Покрыты плоские и вложенные пути, рейтинг,
алиас `ratingCount`, запятая, битый JSON, чужие скрипты, схлопывание пробелов,
массивы верхнего уровня, `@graph` с явным путём и без него.

**Открытый вопрос (решается):** заходить ли в `@graph` без явного пути.

## geonetix-parse-yandex — следующий

Читает карточку организации из встроенного состояния Яндекс.Карт.

**Вход:** HTML страницы `yandex.ru/maps/org/...` + исходный URL.
**Выход:** `Option<LiveMapCardData>` — `None`, если состояние не найдено.

**Где данные:** Яндекс отдаёт большой JSON в `<script>`. Внутри
`stack[].results.items[]` лежит объект организации. Сейчас это единственный
источник данных карточки: JSON-LD на такой странице содержит только `WebSite`
и `BreadcrumbList`, а самой организации в разметке нет.

**Правила:**
1. Перебираются все `<script>`, содержимое которых распознаётся как JSON.
2. Состояние считается найденным, только если в нём есть `stack[].results.items[]`.
3. Берётся первый элемент списка организаций.
4. Название: `title`, затем `shortTitle`.
5. Адрес: `fullAddress`, затем `address`.
6. Описание: `description`, затем `additionalAddress`.
7. Рейтинг: `ratingData.ratingValue`. Число отзывов: `reviewCount`, затем
   `ratingCount`.
8. Категория: `topObjects.categories[].name`, затем `topObjects.rubric.name`.
9. Фото: `photos.count`, иначе длина `photos.items`.
10. Меню: считается по `features` — количество включённых пунктов.
11. Соцсети: `socialLinks[].href`.
12. Внешний сайт: перебираются `urls`, `businessLinks[].href`, `sources[].href`,
    `source[].href`, `url`, берётся первый непустой.
13. Эмоции отзывов: `aspects[]` и `reviewResults.reviews[]`.
14. Пустые части адреса склеиваются точкой.

**Ошибки:** любой сбой разбора → `None`, приложение падает не должно.

**Тесты:** один реальный сохранённый ответ + урезанные варианты, отдельные
случаи на битое состояние и отсутствие массива items.

## geonetix-parse-generic

Разбор любой страницы, когда нет более специфичного парсера.

**Вход:** HTML + `MapPlatform` + URL.
**Выход:** `LiveMapCardData` (всегда, с заполнителями).

**Порядок источников для каждого поля — первый непустой выигрывает:**
- название: `og:title` → `twitter:title` → `<h1>` → `<title>` → JSON-LD `name`
  → название из URL;
- описание: `description` → `og:description` → JSON-LD `description` → адрес из URL;
- адрес: JSON-LD `address.streetAddress` → адрес в тексте → адрес из URL;
- рейтинг и отзывы: JSON-LD `aggregateRating`;
- сайт: `og:url` → JSON-LD `url`.

**Остальные поля:**
- фото: число `<img>`, но не меньше числа слов «фото/photo/gallery» в тексте, максимум 200;
- меню: число слов «меню/каталог/услуги/цены/price» в тексте, максимум 50;
- контакты: найденные телефоны + ссылки `mailto:` + ссылки `tel:` + наличие сайта, максимум 12;
- соцсети: все подходящие ссылки, максимум 10 в выдаче;
- доставка: есть ли «доставка/delivery» в тексте;
- фичи: число слов «доставка/wifi/парковка/акции/бронь/самовывоз/онлайн-запись», максимум 20;
- эмоции: оценка текста отзывов;
- категория: JSON-LD `@type` → эвристика по тексту → название платформы по умолчанию.

**Тесты:** фикстуры на приоритет источников, ограничения максимумов, распознавание
телефонов и соцсетей.

## geonetix-card-source

Слой «получить HTML»: сетевой вызов, кэш, лимиты, запасной путь.

**Умеет:**
- приводить URL к каноническому виду;
- отдавать `RemotePageSnapshot { final_url, body }`;
- отдавать из Redis, если кэш свежий, и писать в кэш после запроса;
- ограничивать частоту запросов;
- при недоступности браузерного воркера уходить на прямой HTTP.

**Не умеет:** разбирать HTML.

**Тесты:** `wiremock` поднимает локальный сервер и проверяет успешный ответ,
редирект, неуспешный код, таймаут и попадание в кэш.

## fetchers/dom-fetch

Маленький Node-скрипт на Playwright. Только получает страницу.

**Умеет:**
- открыть страницу в настоящем браузере и вернуть `{ final_url, body }`;
- вести себя как живой человек: паузы между действиями, прокрутка, переключение
  вкладок, ввод текста с неровным темпом — чтобы не выглядеть роботом;
- возвращать ошибку внятным текстом.

**Не умеет:** ничего извлекать из страницы. Ни одного селектора, ни одного
регулярного выражения.

**Следствие:** тип `BrowserWorkerCardData` (17 полей — копия `LiveMapCardData`)
исчезает совсем. Разбор переезжает в Rust, а воркер отдаёт только HTML.

## Как менять алгоритм

- **Правило приоритета** живёт в одной строке — списке `first_non_empty(vec![...])`.
  Чтобы поменять приоритет источников, правят только этот список.
- **Утилиты выбора** (`select_text`, `select_meta_content`, `count_elements`)
  вынесены отдельно, чтобы парсер выглядел списком правил, а не кашей селекторов.
- **Каждый парсер — чистая функция**: HTML на входе, структура на выходе. Нет сети,
  нет базы, нет общего состояния. Поэтому любой парсер тестируется фикстурой.
- **Фикстуры настоящие**: один реальный успешный ответ сохраняется в репозитории
  и подставляется вместо сети. Онлайн-слой тестируется `wiremock` на локальном
  порту.
- **Реальное поведение фиксируется тестами.** Если парсер возвращает пусто там,
  где должен вернуть значение, это видно по тесту, а не по жалобе пользователя.
## Yandex Maps: recorded response fixture

crates/geonetix-parse-yandex/tests/fixtures/yandex-card.json is a real
successful HTTP response captured from
https://yandex.ru/maps/org/hookahplace_akari/25558422006/, reduced to the
fields the parser reads. Recorded values are unchanged: 183 photos, 150 reviews,
8 menu items, rating 5.0, category Кальян-бар.

The fixture keeps only the stack[].results.items[] branch and drops the
aspect photo lists, review bodies, feature flags, menu item blurbs and the
platform own links. To confirm the reduction changes nothing, the full
recording is parsed alongside the fixture and every LiveMapCardData field is
compared.

Two details matter when rebuilding it:

- The ampersand must be written as a unicode escape, exactly as Yandex does.
  Inside a script element the HTML parser turns a raw ampersand followed by
  booking into an entity and serde_json then rejects the whole state.
- The item must keep type: business. That marker is how the state is told
  apart from ads and other entries.
